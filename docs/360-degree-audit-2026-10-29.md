## Changes applied

The following database migrations were applied to the live Supabase project and mirrored in the repository:

1. [20261029041809 — tighten private table grants and add FK indexes](../supabase/migrations/20261029041809_tighten_private_table_grants_and_add_foreign_key_indexes.sql)  
   Removed unnecessary anonymous grants from private admin tables; restricted social publishing queue/settings and Meta review connection data to server-side access; kept public site-content access read-only; created seven missing foreign-key indexes.

2. [20261029041942 — optimize RLS helper evaluation](../supabase/migrations/20261029041942_optimize_rls_auth_function_policy_evaluation.sql)  
   Rewrote existing `auth.jwt()`, `auth.uid()`, and `auth.role()` policy calls into query-level subselects while preserving policy roles and predicates. The `auth_rls_initplan` performance warning no longer appeared in the subsequent advisor result.

3. [20261029042301 — drop duplicate YouTube history index](../supabase/migrations/20261029042301_drop_duplicate_youtube_history_index.sql)  
   Removed `youtube_publish_history_channel_idx`, which duplicated the retained `(channel_id, created_at DESC)` index.

4. [20261029042530 — lock down future table/sequence defaults](../supabase/migrations/20261029042530_lock_down_future_public_schema_default_grants.sql)  
   Revoked automatic table and sequence privileges for `anon`, `authenticated`, and `service_role` on future objects created by `postgres` in `public`. Existing table grants were not changed by this default-only migration.

5. [20261029042844 — lock down future function execute defaults](../supabase/migrations/20261029042844_lock_down_future_public_function_execute_defaults.sql)  
   Revoked automatic function grants to API roles for future `public` functions and revoked PostgreSQL's global default `PUBLIC EXECUTE` for future functions created by `postgres`. New functions must explicitly grant execution to the roles that need them. Since the global default also affects future functions created in other schemas, migrations that add custom RLS helper functions outside `public` must grant execution explicitly where required.

### Database permission verification after the changes

- Anonymous `SELECT` remains enabled only on the intended public storefront tables: `products`, `categories`, `blog_posts`, and `site_content_blocks`.
- Anonymous writes to `site_content_blocks` are denied.
- Anonymous access to the private admin activity log and post queue is denied.
- Authenticated admin order updates remain permitted subject to the existing RLS/MFA rules.
- Existing order-creation and dispatch-secret RPCs remain executable only by the server-side `service_role`; the existing admin delivery-address RPC retains its explicit admin-email and AAL2/MFA checks.

### Checkout behavior fix

The checkout race timeout in `js/main.js` previously fired after **100 ms**, which could send the customer to the Thank You page before either backend had responded. It now waits up to **1,800 ms**. If no backend has responded by then, the session is stored as pending, the Thank You page presents a pending-verification message, the cart is preserved, and a confirmed `purchase` analytics event is not emitted. When a backend confirms within the wait window, the regular confirmed flow remains.

The order-ID generator was also inspected: it uses `Uint32Array`, so the suspected 8-bit range limitation was not present. The 78 stored order numbers are unique. No order-ID generation change was made.

## Remaining warnings and deferred work

- **Leaked-password protection:** Supabase Auth reports this as disabled. Current Supabase documentation states that leaked-password protection is available on Pro and above; it was not enabled because this project is being kept on the free tier. See [Supabase password security](https://supabase.com/docs/guides/auth/password-security).
- **`pg_net` extension in `public`:** the Security Advisor still warns about its schema placement. It was not moved automatically because scheduled jobs or database dependencies must be inspected first.
- **`admin_update_order_delivery_address` SECURITY DEFINER advisor warning:** it is executable by authenticated users but validates the exact admin email, AAL2/MFA, address, order state, and courier-booking state. The generic warning remains; its custom guard was inspected and the function was not changed.
- **Six RLS-enabled, no-policy tables:** `platform_settings`, `post_queue`, and four YouTube publishing tables are server-only by design. The API roles have no table grants for these tables; Edge Functions use server-side service-role access.
- **Six multiple-permissive-policy warnings:** the reviewed pairs provide separate admin and public/own-record read paths for catalog, blog, profiles, and orders. They were left intact rather than risking changes to customer/admin visibility.
- **Unused-index notices:** 30 informational notices remain. Newly added indexes have little or no usage history yet; they were not removed based only on this metric.
- **Website-publisher release workflow:** a previously validated change set still has `deployment_status=not_started` and is based on an older commit; older drafts are marked conflicted. These were not automatically approved or published. The diff must be rebased/revalidated against current `main`, reviewed, and explicitly approved before publishing.
- **Live browser testing:** direct public-site HTTP/browser verification was not available through the inspection tool in this run. GitHub Pages build/deploy succeeded, but checkout was not submitted live because that would create real test records in the connected systems.

## Maintenance guidance

For future schema changes, add explicit `GRANT` statements only for the exact roles that need access. Before publishing a site change set, validate it against the current `main` commit, review the generated diff, and approve it deliberately. Recheck the Supabase Security and Performance Advisors after the project has received normal traffic so new indexes and the remaining informational findings can be assessed with real usage data.
